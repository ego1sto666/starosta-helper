# Архитектура «Помощника старосты»

Источник подхода: [AWG, «Архитектура сайта: основы проектирования для стабильной работы и роста»](https://www.awg.ru/news/arkhitektura-sayta-osnovy-proektirovaniya-dlya-stabilnoy-raboty-i-rosta/). В статье разделены информационная архитектура (иерархия, навигация, связи, адреса) и техническая (клиент, сервер, база, API). Здесь эти принципы применены к закрытому рабочему приложению для старост, а не к интернет-магазину или публичному каталогу.

## 1. Для кого и для чего

- Староста ведёт одну или несколько учебных групп: расписание, журнал, состав, сдачи, дела и письма преподавателей.
- Заместитель получает доступ только к приглашённой группе. Данные разных групп не смешиваются.
- Без аккаунта приложение работает на одном устройстве и хранит данные в браузере. С аккаунтом локальные данные синхронизируются через API.
- Публичная демонстрация для преподавателя отделена от основного приложения и не содержит аккаунтов и почты.

## 2. Информационная архитектура

Главная → рабочие разделы → конкретная запись или действие. Главная показывает, что требует внимания сегодня; каждое уведомление ведёт прямо к нужному экрану. Карта основных разделов и вкладок находится в `js/routes.js`, чтобы подписи и адреса не расходились.

```text
Сегодня #home
├─ текущая/следующая пара → Журнал → отметка #mark/{lessonId}/{date}
├─ ближайшие сроки → Учёба / Внеучебка → запись
└─ настройка новой группы → Мастер #setup
Журнал #journal
├─ день и пара → Отметка #mark/{lessonId}/{date}
└─ Итоги посещаемости #stats
Группа #group
├─ Студенты → Карточка #student/{id}
├─ Преподаватели #group/teachers
└─ Подгруппы #subgroups[/{subject}]
Учёба #study
├─ Сдачи #study/works
├─ Сессия #study/exams
└─ Оценки #study/grades
Внеучебка #tasks
├─ Дела #tasks
├─ Сборы #tasks/funds → Деньги / Документы
├─ События #events
└─ Опросы #tasks/polls
Настройки #settings
├─ Аккаунт #account
├─ Почта преподавателей #mail
├─ Шаблоны сообщений #templates
└─ Справка #help
```

Правила навигации:

1. Пять рабочих разделов доступны из постоянного меню; настройки — из отдельной кнопки. Внутри раздела вкладки видны сразу.
2. Типовое действие должно открываться за 2–3 перехода: «Сегодня → пара → отметка», «Группа → студент», «Настройки → почта». Глубокая ссылка открывает запись без прохода через главную.
3. У вложенного экрана есть заголовок и путь назад; важные связи показываются на самой карточке (например, отметка → распределение по подгруппам).
4. Адреса приложения — читаемые hash-маршруты. Старые `#schedule`, `#tasks/works`, `#tasks/exams` перенаправляются на актуальные экраны. Параметры записей кодируются через `encodeURIComponent`.
5. Частные экраны не индексируются поисковиками. Для этого приложения внутренние ссылки нужны пользователю и работе прямых ссылок, а не распределению SEO-веса.

## 3. Техническая архитектура

```text
Телефон / ПК: PWA (HTML, CSS, JS, service worker)
  ├─ экраны и действия: js/app.js
  ├─ карта разделов: js/routes.js
  ├─ API и слияние изменений: js/api.js
  ├─ настройки API: js/config.js
  ├─ локальные данные: localStorage; фото справок: IndexedDB
  └─ кэш оболочки и офлайн: sw.js
                  │ HTTPS + cookie
                  ▼
Caddy: статические файлы и /api/* → FastAPI
  ├─ auth: аккаунты и сессии
  ├─ groups: доступ к группам, версии данных, приглашения
  ├─ mail: источники и предложения из писем
  ├─ worker: периодическая проверка IMAP и очистка
  ├─ inbound: приём пересланных писем (после настройки домена/MX)
  └─ PostgreSQL в развёртывании; SQLite при локальной разработке
```

Поток данных: действие пользователя меняет локальную модель → `persist()` сохраняет её в браузере → `js/api.js` отправляет версию группы в API → API проверяет сессию и право доступа → сохраняет новую ревизию в базе. При конфликте версий клиент сливает изменения и повторяет отправку (`server/design/sync.md`). Без связи локальная работа продолжается.

Поток почты: IMAP или пересылка → сервер связывает письмо с группой → сверяет адрес отправителя с преподавателями группы → создаёт предложение → староста принимает или отклоняет его на экране «Почта». Содержимое писем не публикуется в демонстрации (`server/design/mail.md`).

## 4. Границы и хранение

| Ответственность | Где находится сейчас | Правило |
|---|---|---|
| Интерфейс, быстрые действия, офлайн | `index.html`, `css/`, `js/app.js`, `sw.js` | Не хранить серверные секреты в браузере |
| Навигация и адреса | `js/routes.js`, обработчик маршрутов в `js/app.js` | Разделы и вкладки добавлять в карту |
| Обмен и конфликты | `js/api.js`, `server/app/routers/groups.py` | Каждая запись группы имеет ревизию |
| Аккаунты и права | `server/app/routers/auth.py`, `server/app/deps.py` | Любой запрос к группе проверяет членство |
| Письма | `server/app/mail/`, `server/app/routers/mail.py`, `server/app/worker.py` | Источники и письма принадлежат конкретной группе |
| Данные | `localStorage`, `server/app/models.py` | Сервер хранит одну JSON-копию данных группы плюс отдельные таблицы аккаунтов и почты |

На текущем этапе нужен один сервер приложений и одна реляционная база. Разделение на микросервисы и балансировщики из примера AWG для этого масштаба преждевременны: они добавят сетевые зависимости и эксплуатационную работу без измеренной нагрузки. Модульный API уже отделяет аккаунты, группы и почту; при росте можно масштабировать API и worker по отдельности после измерения нагрузки.

## 5. Состояние и следующий этап

**Работает локально:** PWA, офлайн-данные, мастер группы, импорт, аккаунты, синхронизация и IMAP через `Открыть с аккаунтом.bat`. Есть тесты браузера и API. Отдельная демонстрация опубликована без сервера.

**До публичного запуска:** миграции базы вместо `create_all`, резервные копии и восстановление, домен/HTTPS, проверка конфигурации и прав на сервере, доставка писем для восстановления пароля, проверка реального почтового ящика и вложений, публикация документов по обработке данных, пилот на нескольких группах. Эти пункты перечислены в `ROADMAP.md`; наличие Docker Compose само по себе не означает готовый публичный сервис.

**Проверка архитектуры:** при изменении навигации проверять прямые ссылки и путь назад; при изменении модели — миграцию старых локальных данных и синхронизацию; перед публикацией — отсутствие личных файлов в статической сборке. Производительность и потребность в масштабировании оцениваются по замерам, а не по общим цифрам из статьи.
